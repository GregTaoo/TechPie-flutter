## 问题与修复

原预约记录查询在一次 30 秒请求内串行执行“每个场地 × 每个时段”的学校查询，每个 API 请求又重新建立 OA 会话。选择所有场地和多个小时会放大网络往返，最终出现截图中的 `TimeoutException`。

新版后端只提交一次日期查询，依据学校返回的实际场地和时段分组。XML 按真实页数读取，后续页面最多并发四个。学校 `pageIndex` 从 **1** 开始，0 和 1 都返回第一页；从 1 读取至 `pagenum`，再核对 `recordCount`，避免重复第一页、漏最后一页或静默截断。

客户端在当前账号和 eGate 登录态的内存中复用 OA Cookie，登出、解绑或登录态变化时清除。旧后端没有 `bulkSearch` 能力标记时，客户端使用最多三个并发任务，每次只查询一个场地和至多三个时段，避免旧实现的一次大请求超时。

预约可用性按小时返回进度，树形选择器请求顺序执行。切换日期、运动或时间范围会废弃旧结果并停止尚未开始的旧查询。缺少分类或结果时明确报“状态未知/结果不完整”，不能当作“已满/没有预约”。预约提交超时提示先查询记录，不自动重复提交。

## 物理场地规则

| 用户选择的运动 | 可预约实际场地 | 提交到学校的原生类别和编号 |
| --- | --- | --- |
| 网球 | 网球场1、2、3号 | `tennis` / 1、2、3 |
| 网球 | 匹克球1号场地 | `pickleball` / 1 |
| 匹克球 | 匹克球1号场地 | `pickleball` / 1 |
| 匹克球 | 网球场1号 | `tennis` / 1 |

网球显示四个选项，匹克球显示两个选项，并保留实际场地名称。匹克球二号（学校 ID 44）不出现在查询、可用性和预约选择中。同一物理场地同一时段在两个运动分组中互斥选择，提交时再次去重。

后端 availability/book 保持原生类别合同，客户端负责把运动选项转换为实际场地：网球选项4提交 `pickleball / 1`，匹克球选项2提交 `tennis / 1`。Python 参考项目采用相同映射。

## OA 个人信息自动同步

场馆顶部两种平台布局的“个人”均改为“个人信息”。绑定、重新绑定 eGate 及启动后，客户端独立请求新增 `/api/oa/gym/profile`；同步不阻塞登录、预约可用性或预约记录查询，也可手动点击“从 OA 同步”。

学校个人卡片的手机号实测已被服务端掩码，并非只在前端隐藏。后端从不带人员 ID 的自身资料入口解析当前用户资源 ID，再读取自己的个人卡片；联系方式缺失时只读 GET 自己的联系资料表单，取得完整手机号和邮箱。不提供查询其他人员联系方式的参数，不修改学校资料。

预约联系人按 TechPie 主账号与 eGate 学号共同隔离。自动同步更新空白字段和上次由 OA 提供的字段，保留用户手动修改；同步期间手动保存、换绑或登出后到达的旧响应均不能覆盖当前资料。旧的全局联系人缓存保留但不自动分配给新账号，预约也不再回退使用 TechPie 主账号手机号。旧后端无新接口时明确提示手动填写，查询和预约继续可用。
